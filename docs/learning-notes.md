# 从零搭建 Coding Agent：阶段复盘

## 起点

开始这个项目时，我对 Agent 的理解比较模糊，容易把它等同于“模型加几个工具”。完成 CH2–CH6
后，我更倾向于把 Agent 理解为一个受约束的状态机：模型负责提出下一步，工程系统负责保存
状态、验证动作、执行工具、处理错误，并决定是否继续。

## 最大的坑

我现在认为，AI 工程最大的坑是**不确定性会沿着调用链累积，但表面结果仍然可能显得合理**。

例如：

- 模型说“已修改”，工具可能根本没有执行。
- 工具执行成功，结果却没有正确回灌，下一轮模型仍按旧信息行动。
- 单文件实现看似完整，但没有接入 App 或 Agent 主流程。
- Prompt 写了限制，模型仍可能在长上下文中忽略它。
- AI-assisted coding 很快生成大量代码，也会更快生成错误的完成感。

因此，Agent 项目不能只评估最终回答，还要让中间状态可观测、可限制、可重放。

## 学到的核心结构

### ConversationManager

它不是简单的字符串列表，而是 Provider 与 Agent 之间的稳定边界。文本、思考、工具请求和工具
结果需要保持结构化，同时能序列化成不同 Provider 的协议。

### Agent Loop

核心循环是：

```text
模型流式输出 → 收集工具调用 → 权限判断 → 执行 → 结果回灌 → 下一轮模型调用
```

需要额外处理最大轮次、取消、未知工具、工具失败、并发、安全边界和 token 增长。循环中的每一个
停止条件都比“再调用一次模型”更重要。

### Tool Contract

工具必须有统一 schema、参数校验、类别和结构化结果。只有这样，Provider、权限系统、TUI 和测试
才能围绕稳定接口协作。

### Permission System

安全不能只写在 System Prompt 中。危险命令和路径沙箱属于确定性代码；不确定操作再交给规则、
模式或 HITL。YOLO 也应明确哪些层可以跳过、哪些层不可跳过。

## 对 vibe coding 的重新理解

Vibe coding 的价值是快速探索和验证，但风险是模型在缺少边界时自行补全需求。有效的方式不是
无限追加 Prompt，而是给任务建立外部结构：

1. `spec.md` 固定需求、边界和 Out of Scope。
2. `tasks.md` 把实现拆成有依赖关系的小交付。
3. `checklist.md` 要求每项都可观察、可运行。
4. `api-contract.md` 在编码前固定模块之间的请求、响应和错误语义。
5. 测试和静态检查验证 AI 的完成声明。

这套方式不能消除错误，但能把“感觉完成了”转换成“有证据地完成了”。

## 当前取舍

- 优先交付可演示的单进程 TUI，而不是先做分布式 Agent 平台。
- 使用静态规则与 HITL，不训练安全分类模型。
- 自动记忆采用可审计的 Markdown 笔记，不宣称已经解决语义记忆或知识图谱。
- Hook 采用有限条件 DSL 和固定 Action 类型，不引入任意 Python 表达式执行；自动化失败只产生
  通知，不能拖垮 Agent 主流程。
- CH14 已用 Git worktree 补上文件系统隔离：不使用全局 `chdir`，每个 Agent 的核心工具绑定
  独立 work_dir；长期 Team 仍保留到 CH15，避免把单进程隔离伪装成分布式能力。

## 下一步

如果继续迭代，优先级不是堆更多工具，而是：

1. 用 MCP 建立标准外部工具边界。
2. 做项目级上下文选择，降低无关 token。
3. 设计可解释、可删除、可验证的跨会话记忆。
4. 在 CH15 AgentTeam 前先验证 worktree 分支的合并冲突、磁盘成本和长期清理策略。
