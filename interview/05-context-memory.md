# 05 上下文与记忆：又贵又健忘，怎么办

## 问题用大白话说

每调一次模型，都要把**到目前为止的对话**再寄一遍。Agent 一任务几十轮，工具输出又长，窗口会满、账单会炸、模型还会「越聊越傻」。

另外：关了终端再开，它不该把你的缩进偏好、这个仓库用 pytest 全忘了。

所以有两套东西，别混：

| | 解决什么 | 本仓库 |
|---|---|---|
| 上下文管理 | **这一次会话**怎么塞得下、怎么不炸协议 | `context/manager.py` |
| 记忆 | **跨会话**还知道项目和你的习惯 | `memory/` + `SIMPLECODE.md` |

---

## 两层压缩（能轻则轻）

### 第一层：大结果落盘，不调模型

工具输出太长 → 原文写到 `.simplecode/session/tool-results/`，历史里只留预览 + 路径。  
单条超限先压；一轮里好多中等结果加起来超，再挑最大的落盘。

- 不丢信息（磁盘上还在）
- 不花钱
- 模型真要全文，自己 `ReadFile` 那条路径

Read 文件往往希望看全文，实现上会对「单条上限」放宽，避免刚读完就被剪成渣。

### 第二层：自动摘要，要花钱

每轮前看 token。超过阈值（窗口先扣一块给摘要输出和本轮余量，不是等到 100%）：

- 让模型写结构化摘要
- 历史换成「摘要 + 边界标记」
- 重新注入环境、指令、记忆
- 摘要失败：若是 prompt-too-long，丢掉最早约 1/5 **整轮**再试，最多 3 次
- 再失败：熔断，不再自动压，避免死循环烧 API；`/compact` 仍可用

主循环里如果 API 已经报「上下文太长」，还会再强制 compact 重试，最多 2 次。

**压缩必须切在完整轮次上。** 把 `tool_use` 留下、`tool_result` 剪掉，下一轮协议错误。这是上下文章节的得分点。

## 记忆三层（课程叫书架）

1. **`SIMPLECODE.md`（人写的项目指令）**  
   启动注入。团队约定、怎么跑测试。跟仓库走，适合进 git。

2. **JSONL 会话**  
   完整流水账，追加写。崩溃好恢复，也能 grep。选 JSONL 不是炫技：Agent 写入是纯追加，不需要 SQLite 锁。

3. **自动记忆 `memories.md`**  
   隔几轮异步抽：用户偏好、纠正、项目知识、参考资料。  
   **用户级**（家目录，跨项目：4 空格、中文注释）  
   **项目级**（`.simplecode/`，仅本仓库：用 PostgreSQL、测命令是 pytest）

注入位置：对话历史开头、环境信息后面；压缩后重注。整段记忆不当 system prompt——那是角色；记忆是用户侧背景。

局限要主动说：记忆会变脏、没有自动过期，用户可直接改 markdown。这不是知识图谱，别吹。

---

## 和 CLAUDE.md / SIMPLECODE.md 的区别

| | 谁写 | 干什么 |
|---|---|---|
| 项目指令 | 人，版本可控 | 显式规范 |
| 自动记忆 | Agent 从对话里抽 | 隐式偏好、纠正 |

两者都注入，一个团队共识，一个个人经验。

## 口述 60 秒

> 上下文不是越多越好。我先把大工具结果落盘只留预览，快满了再摘要，摘要本身也预留 token，失败就按整轮丢最老的并熔断。压缩对齐 tool 配对，否则协议炸。跨会话靠人写的 SIMPLECODE.md、JSONL 流水、自动抽取的两层记忆。UI 和磁盘可以留全量，给模型的永远是预算内投影。
