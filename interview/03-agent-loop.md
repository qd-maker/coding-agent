# 03 Agent Loop：它怎么自己干活、怎么停、怎么不把协议搞坏

## 人话

没有 Loop，模型只能「问一句答一句」。有了 Loop，它变成：

> 想一步 → 动手 → 看结果 → 再想一步 → … → 只说话不再动手，结束。

这就是 ReAct：Reasoning + Acting。状态在对话历史里延续，不是每次从零猜。

本仓库入口：`simplecode/agent.py` 的 `Agent.run`。

---

## 一轮里实际做什么（按代码顺序讲）

打开 `run()` 对着讲：

1. **收邮箱**（多 Agent 时）：队友消息先写进历史。
2. **刷新环境**：cwd、已激活 Skill 等钉在历史开头。
3. **Layer 1 预算**：过大的 tool 结果落盘，历史里留预览。
4. **Layer 2 摘要**：接近窗口就 `auto_compact`；失败有熔断，连续失败会停自动压。
5. **Plan Mode reminder**（如果在 Plan）。
6. **调模型** `client.stream`，TUI 边收边画。
7. **看这一轮有没有 tool_calls**：
   - 没有：可选完成验证（改过文件/跑过命令才检查证据）→ `LoopComplete`
   - 有：按并发安全分批 → hook → 权限 → 执行 → 把结果按 **同一个 tool_id** 写回
8. **进入下一轮**，直到停。

人话记忆口诀：

```text
先收拾桌子（压缩）→ 再问工头（模型）→ 工头要工具就过安检再干 → 把回执钉在工单上 → 再问
```

---

## 它怎么知道该停了？

**主信号不是 `stop_reason`。** 有的接口这个字段不可靠。本仓库看：**这一轮实际有没有 tool_calls**。

- 有 → 还要干活
- 没有 → 它认为做完了（或在解释）

**程序必须再加兜底**，否则会空转烧钱：

| 兜底 | 本仓库 |
|---|---|
| 最大轮次 | `max_iterations` 默认 50 |
| 连续未知工具 | 3 轮就停 |
| 输出被截断 | `max_tokens` 时抬上限或续写，有次数上限 |
| 上下文爆了 | 捕获 prompt-too-long，强制 compact，最多 2 次 |
| 用户取消 | Ctrl+C 取消 worker，并补齐未完成的 tool_result |
| 完成门 | 改过代码的任务会核对「是否真的写了/测了」，失败最多修 2 次 |

面试加一句自己的体感：

> 我遇到过模型陷在改代码–跑测试里出不来。从那以后我不再相信「它自己会停」，轮次上限和未知工具熔断是必须的。

---

## 最容易炸的点：tool_use 必须成对

Function Calling 的硬规矩：

```text
assistant 说「我要调工具 X，id=abc」
下一轮 user 必须带「abc 的结果」
缺一个、多一个、id 对不上 → API 直接报错，会话废
```

会破坏配对的真实场景：

- 用户在工具跑到一半按 Ctrl+C
- 模型这一轮报错 / 换模型重试
- 压缩把 use 和 result 切到两段
- 从 JSONL 恢复时日志写到一半进程死了

本仓库怎么守：

1. 循环里取消/异常：`_seal_open_tools` 给没返回的调用补一条错误结果
2. 每轮发给模型前：`ensure_tool_result_pairing` 再扫一遍（缺的补、孤儿丢掉）
3. 压缩按「一轮」切，不从配对中间砍

这是「你真写过才知道」的题。教程很少写 ESC 会搞出孤儿 tool_use。

---

## 流式：模型还在说，界面就该动

`client.py` 把两家协议收成统一事件：`TextDelta`、`ThinkingDelta`、`ToolCallStart/Complete`、`StreamEnd`。

TUI 曾经有个体验坑：字到了内存，屏幕 40ms 节流刷一次，后半句赶上跑工具，界面就停在半句话，等整轮结束才一次性出来。后来改成：离开文本事件立刻刷尾巴，后台 0.1 秒再补刷。面试如果被问体验，可以提这个，显得你在用自己的产品。

---

## 完成门（别把它讲成「又调了一次玄学」）

改文件、跑命令这类任务，模型说「写好了」不一定真写了。`evidence.py` 会看本轮是否有成功写入、是否有测试/编译证据。失败就塞一条 reminder 让它修，最多两次，再失败以 `verification_failed` 结束，**不能装成功**。

解释型问题（「这函数干什么」）走 `answered`，不强制验证。

---

## 和 Plan Mode 的关系

Loop 机制不变，变的是**这一轮允许哪些工具、权限模式是什么**。

- `/plan`：只读 + 写计划文件。先想清楚再动手。
- `/do`：回到 Accept Edits，计划文本还在上下文里当锚点。

这是 Plan-and-Execute：规划一次，执行多步。和纯 ReAct 比更省、更可控；发现计划错了允许偏离，但应说出来。

---

## 口述 90 秒

> Loop 就是 while：先按预算投影历史，再调模型。我不以 stop_reason 为准，只看这一轮有没有 tool_use。有就校验、过权限、执行，结果用同一个 id 写回再循环。没有就认为说完了。停不下来靠最大轮次、连续未知工具、压缩熔断。最难的是协议完整性：中断、压缩、恢复都可能留下半截 tool_use，所以取消要补错误结果，发送前再配对检查。模型负责想，工程负责不让账本记花。
